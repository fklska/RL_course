# Карточка проекта K04 · среды

## Исследовательский вопрос
В каких случаях предсказание BFS (число шагов и результат(успех / провал)) расходится с реальным исходом в базовой и модифицированной версии BabyAI-UnlockToUnlock-v0?

## Данные и срез
* Среда: `BabyAI-UnlockToUnlock-v0` (пакет `minigrid-3.2.0`);  
* Лицензия: Apache-2.0   
* Seed: [0, 1, ..., 499]  
* число тестовых конфигураций: N=500  
* max_steps = 1080  
* правило отбора: конфигурации среды должны быть уникальны    

## Эталон и метод
- Эталон: проигрывание той же последовательности действий в реальной среде  
- Оцениваемый оценщик: BFS по модели переходов    
- Базовое сравнение: упрощённый BFS  

## Метрика и критерий
- Метрика ошибки: Частота ошибок = (траектории, где предсказание BFS разошлось со средой хотя бы по одному полю: успех/неуспех, шаг завершения, итоговое состояние) / (все проверенные траектории)
- Численный критерий успеха:  
  - на оптимальных путях (группа 1) совпадение 100%: среда детерминирована, поэтому любое расхождение означает ошибку модели. При 0 ошибках на 500 конфигурациях верхняя 95% граница частоты ошибок ≈ 3/500 = 0,6% (правило трех)  
  - на группах 2-3 совпадение не ниже 99% - каждое расхождение разобрано и отнесено к конкретному правилу среды  
  - упрощённый BFS (базовое сравнение) ошибается заметно чаще, иначе наш тест не чувствителен (проверка, что вообще есть смысл сравнивать оценщик с базовым сравнением)


## Риск и границы
- Возможная ошибка оценщика: BFS может быть неверно реализован или использовать другую модель переходов, чем реальная среда. 
- За границами проекта: Разработка новых RL-алгоритмов, сравнение архитектур нейросетей, стохастические среды

## Сравнение моделей BFS

`python -m scripts.bfs --seeds 10` запускает полный BFS (`full`) и упрощённый
(`baseline`) на одинаковых начальных картах. Каждый план отдельно проверяется
в настоящей MiniGrid с тем же seed. Вывод содержит длину плана, реальный успех,
число выполненных шагов и совпадение успеха и длины (`match`). Итоговое состояние
эта проверка пока не сравнивает.

- `transition_full`: ключ должен совпадать с дверью по цвету; для подбора
  предмета агент должен смотреть на него.
- `transition_baseline`: любой ключ открывает любую запертую дверь через
  `toggle`; ключ можно подобрать из любой из четырёх соседних клеток.
  При нескольких доступных предметах порядок: спереди, справа, сзади, слева.
  Спереди подбирается обычный предмет, с остальных сторон — только ключ.
  Мяч по-прежнему нужно подбирать, глядя на него; занятые руки мешают подбору.

`solve(env, transition_fn=transition_full)` принимает модель переходов.
Вызов `solve(env)` и `render.py` по умолчанию используют полную модель.

## Пункт 1: оценка фиксированных планов

Поиск и оценка разделены:

- `solve(env, transition_fn)` ищет план по выбранной модели.
- `evaluate(env, actions, transition_fn)` предсказывает результат готового
  плана; не ищет замену и не изменяет переданную среду.
- `replay_result(seed, actions)` выполняет тот же план в свежей MiniGrid.
- `replay(seed, actions)` сохраняет прежний интерфейс `(success, steps)`
  для совместимости.

`Evaluation` содержит `success`, `steps`, `terminated`, `truncated` и
`final_state`. Последнее поле — позиция, направление, предмет в руках,
состояния дверей и предметы на карте. Стены и цвета дверей фиксированы
в рамках конфигурации. Предмет в руках теперь читается из настоящей среды,
что позволяет оценивать промежуточные состояния.

Успех — подбор мяча. Если действия закончились раньше успеха, вердикт —
неуспех, но `terminated` и `truncated` могут оставаться ложными: неуспех
плана не обязательно означает завершение эпизода. Учитывается оставшийся
лимит `max_steps - step_count`. При успехе на последнем разрешённом шаге
оба флага могут быть истинны, как в MiniGrid. После успеха или тайм-аута
оставшиеся действия не исполняются. Поддерживаются действия 0–5.

Режим аудита: оба оценщика получают один и тот же план из выбранного источника.
`match` здесь сравнивает все поля `Evaluation`, включая конечное состояние
и флаги завершения; это более строгая проверка, чем в режиме планировщиков.
Отсутствие найденного плана отмечается отдельно и не включается в число
оценённых траекторий; вывод содержит и этот счётчик, и запрошенное число seeds.

```powershell
python -m scripts.bfs --audit --plan-source full --seeds 3
python -m scripts.bfs --audit --plan-source baseline --seeds 3
python -m unittest discover -s tests -v
```

Исходный режим `python -m scripts.bfs --seeds 3` по-прежнему сравнивает собственные
планы двух планировщиков. Он не заменяет аудит одинаковых траекторий.

### Границы текущей реализации

Модель рассчитана на `BabyAI-UnlockToUnlock-v0` с ключами, дверями и одним
целевым мячом; это не универсальный симулятор всех заданий MiniGrid.

`final_state` — общее представление существенных игровых полей, а не
полная сериализация среды с генератором случайных чисел и верификатором.

## Пункт 2: 52 начальные конфигурации

В `data/configurations.jsonl` сохранены 52 уникальные начальные конфигурации
`BabyAI-UnlockToUnlock-v0`. Каждая JSON-строка содержит:

- `id`: `K04-001` … `K04-052`, устойчивый идентификатор в зафиксированном наборе;
- `group`: `core` для первых 20 записей, `second` для остальных 32;
- `seed`: seed генерации;
- `env_id`, `schema_version` и `versions`: среда, версия формата и версии
  Gymnasium/MiniGrid, необходимые для воспроизводимости;
- `initial_state`: размеры, полная карта, позиция и направление агента,
  предмет в руках, текст цели, лимит и счётчик шагов;
- `fingerprint`: SHA-256 канонического JSON из `env_id` и `initial_state`.

Карта использует стандартную кодировку MiniGrid:
`grid[x][y] = [тип объекта, цвет, состояние]`. Для интерпретации используются
таблицы `OBJECT_TO_IDX`, `COLOR_TO_IDX` из `minigrid.core.constants`;
для дверей 0 — открыта, 1 — закрыта, 2 — заперта. Это начальные состояния,
а не результаты выполнения или частичные наблюдения агента.

### Правило отбора и уникальность

Кандидаты перебираются по seed, начиная с 3. Seeds 0–2 исключены как известные
разработчикам технические примеры. Берутся первые 52 состояния с различным
`fingerprint`; дубликаты пропускаются. Seed, ID, группа и версии библиотек
не входят в отпечаток состояния, поэтому два одинаковых состояния с разными
seed не будут приняты за разные конфигурации. Цвета, ориентация агента,
расположение предметов, цель и лимит шагов входят в сравнение. Эквивалентность
после поворотов карты или переименования цветов отдельно не проверяется.

В сохранённом наборе получились seeds **3–54**, дубликатов не встретилось:

| Группа | ID | Seeds | Число |
|---|---|---|---|
| `core` | `K04-001` … `K04-020` | 3–22 | 20 |
| `second` | `K04-021` … `K04-052` | 23–54 | 32 |

Выбор и деление на группы детерминированы, не зависят от успеха BFS или
совпадения оценщиков. Это учебный срез, а не случайная репрезентативная
выборка всех возможных сред. ID соответствует зафиксированному набору;
для проверки идентичности конкретного состояния используется отпечаток.
После начала разметки записи и их ID не перенумеровывать.

### Запуск и воспроизведение

В активированном окружении с версиями из `requirements.txt`, из корня проекта:

```powershell

python -m scripts.generate_configurations --verify
python -m unittest discover -s tests -v
```

Для подготовленного ранее окружения замените `python` на
`.\.venv\newer\Scripts\python.exe`.

Генератор сохраняет только целый набор; если лимита кандидатов не хватает,
он сообщает об ошибке. Повторный запуск с теми же данными оставляет файл
без изменений. Если существующий файл отличается, генератор отказывается
его перезаписывать. `--verify` заново создаёт каждую карту по seed и сравнивает
всю запись, включая версии, ID, группу, отпечаток и начальное состояние.
Поэтому смена версии MiniGrid не останется незамеченной.

### Как сформированы траектории

На каждую из 52 конфигураций назначена одна последовательность действий.
Чтобы набор не состоял только из заведомо хороших планов одного алгоритма,
источники смешаны **до запуска оценщиков**, без отбора по их вердиктам:

| Источник последовательности | core | second | Всего |
|---|---:|---:|---:|
| План полного BFS | 10 | 16 | 26 |
| План упрощённого BFS | 5 | 8 | 13 |
| Первая половина плана полного BFS | 5 | 8 | 13 |

Для укороченного плана оставляется `max(1, len(plan) // 2)` действий.
Назначения перемешиваются отдельно внутри групп с фиксированными seed
2026111701 и 2026111702. Это seed распределения источников, не seed среды.
Правило зафиксировано в `source_schedule`; отсутствие найденного плана
считается ошибкой подготовки, а не поводом незаметно заменить объект.

Генерация плана не равна выдаче оценки. После фиксации действий и полная
модель, и baseline получают **одинаковые начальное состояние и действия**.
Программа выгрузки не перепланирует маршрут. Источник конкретного плана
не указан в `slice.jsonl` и карточках. Разметчикам не следует изучать алгоритм
подготовки для угадывания источника — они проверяют настоящие правила.

Это целевой учебный набор, а не оценка естественной частоты ошибок на
случайных действиях. Пропорции источников не являются результатами аудита
и не задают заранее человеческие метки.

### Формат и просмотр

Обязательные для задания поля каждой строки — `id`, `group` и содержимое
объекта. Здесь содержимое находится в `content`: цель, координаты, текстовая
карта, предметы, ориентация, лимит и все нумерованные действия. Поле пригодно
для показа даже без HTML. Дополнительно сохранены `env_id`, `seed`,
`configuration_fingerprint`, `versions`, `initial_state`, числовые `actions`
и относительные пути `materials.page` / `materials.map`.

Откройте **`audit/materials/index.html`** обычным браузером, прочитайте
инструкцию и перейдите к назначенному ID. Интернет и Python для просмотра
не нужны. Карточки показывают только начальную карту и заданные действия;
они не содержат прогнозов оценщика, анимации исполнения, награды или готового
исхода. Страница не собирает ответы: их вносят в CSV учебного ноутбука.

При переносе в Colab загрузите `slice.jsonl` и `instruction.md` в `audit/`.
Для локального просмотра передайте разметчикам всю папку `audit/`, включая
`materials/`. Учебный ноутбук пока не предоставлен: чтение этих полей именно
его интерфейсом и допустимость текстовых меток нужно проверить при первом
запуске. Известные требования задания к JSONL соблюдены; внешний авточекер

его копируют в `audit/` под тем же именем и добавляют в итоговый комплект.
До этого не хранить его в общей `audit/`, не печатать метки в отчётах.

### Команды воспроизведения

Из корня репозитория в окружении с `requirements.txt`:

```powershell
python -m scripts.prepare_audit
python -m unittest discover -s tests -v
```

Первая команда не перезаписывает изменившийся `slice.jsonl`, карточки или
карты; повторная подготовка тех же данных оставляет их содержимое прежним.
Инструкция редактируется отдельно; генератор не заменяет согласованную
версию автоматически. После начала разметки не менять действия, ID и карты.

Следующие команды выполняет ответственный за скрытые ответы, не разметчик:

```powershell
python -m scripts.export_predictions --model full --output "D:/ИТМО/3 семестр/RL/scorer/scorer.jsonl"
python -m scripts.export_predictions --model baseline --output "D:/ИТМО/3 семестр/RL/scorer/baseline_predictions.jsonl"
```

Экспорт проверяет все конфигурации и версии по seed, соответствие текста
числовым действиям, ID и группы. Он отклоняет путь внутри общего репозитория,
не перезаписывает отличающийся файл и выводит только число записей и путь.
